# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Full-stack fitness tracker: Expo/React Native client (`frontend/`, mobile + web) and a Spring Boot REST API (`backend/training-backend/`) on PostgreSQL.

## Commands

### Frontend (`frontend/`)
- `npm ci` then `npm run start` (Expo dev server; `w` for web). `npm run web` for web only.
- Checks CI runs: `npx tsc --noEmit`, `npm run lint` (ESLint, `eslint-config-expo` flat config)
  and `npm test` (Jest with the `jest-expo` preset). Lint runs with `--max-warnings 0`, so warnings fail CI.
- Unit tests cover the pure logic in `utils/` and sit next to each module as `*.test.ts`; shared
  data builders are in `test/factories.ts`. Single file: `npm test -- utils/muscles.test.ts`.
- Imports use the `@/` alias for the `frontend/` root.

### Backend (`backend/training-backend/`, Java 21, Gradle wrapper)
- Local DB: `cd backend && docker compose up -d` (needs `backend/.env`, copied from `backend/.env.example`).
- Run: `./gradlew bootRun` (port 8080). The `local` profile is active by default and reads `application-local.properties`, which is gitignored and holds `jwt.secret`, the datasource password and CORS origins; copy it from `application-local.properties.example` next to it. The README's "Run Locally" is the setup for a new machine; keep it in sync when local config changes.
- Tests: `./gradlew test`. Single test: `./gradlew test --tests 'de.mornhinweg.trainingbackend.controller.AuthControllerTest'` (append `.methodName` for one method).
- Tests are `@SpringBootTest` against a throwaway Postgres started by Testcontainers (needs Docker; not the dev DB). Every `@SpringBootTest` class must `@Import(TestcontainersConfiguration.class)`. `src/test/resources/config/application.properties` activates a `test` profile (not `local`) and supplies `jwt.secret`, CORS and high rate limits, so tests never read a machine's `application-local.properties` and behave the same in CI, worktrees and on every machine.

### Running the app
- The `run-app` skill (`.claude/skills/run-app/`) starts db/backend/web, seeds a user with history and drives the web build in headless Chrome (screenshots, taps, swipes, page text, console errors). Use it to check UI changes.

### Android builds
- `.github/workflows/android-build.yml` (manual `workflow_dispatch` with a profile input) runs `eas build --local` on the Actions runner and attaches the `.apk` to a GitHub release. Signing credentials come from EAS (`EXPO_TOKEN` secret). Build profiles live in `frontend/eas.json`.

### Deployment
- Root `docker-compose.yml` + `.env` (see `.env.example`) runs Postgres, the backend with the `prod` profile, and an Expo web export served by Nginx on port 8082. Nginx proxies `/api` to the backend. The backend has a Docker healthcheck on `/actuator/health/readiness` (Actuator exposes only health, without details, and it is not proxied), and the frontend waits for it via `condition: service_healthy`.

## Architecture

### Backend
- Layered: `controller` → `service` → `repository` (Spring Data JPA), with request/response DTOs under `dto/<domain>/`. Lombok is used throughout.
- Domain hierarchy: `User` → `TrainingSplit` (one active per user; tracks a current block) → `Workout` (a named training day) → `Exercise` (the workout's plan: sets/reps/weight, ordered by `orderIndex`). Each `Exercise` links to a per-user `LibraryExercise` that holds its name, notes, video and rep unit. Entries are shared across workouts and unique per user ignoring case, and progress and "previous session" values are aggregated per library entry. Library entries also carry primary/secondary muscles (shoulders split into front/side/rear delts), usually copied from the read-only, global `exercise_catalog`. That table is seeded by a migration generated with `backend/scripts/generate_exercise_catalog.py` from free-exercise-db. A library entry can link the catalog exercise it was picked from (`catalogExerciseId`). About 200 catalog exercises have an Everkinetic line drawing (CC BY-SA 4.0, mapped by hand in `backend/scripts/generate_exercise_illustrations.py`), whose start and end poses `ExerciseIllustrationService` serves as SVG from `/api/exercise-catalog/{id}/illustrations/{0|1}`. The app recolors them and must show the credit (`IllustrationCredit`). Weekly sets per muscle are computed on the client from the history (`utils/muscles.ts`). A `TrainingLog` is a session started from a workout and holds `ExerciseLog`s.
- A split can have an optional mesocycle (`mesocycleWeeks`, `mesocycleStartDate`; independent of the manual `currentBlock`), whose last week is a deload and which repeats on its own. The week is derived from the start date and the client's local date (`Mesocycle` on the server, `utils/mesocycle.ts` on the client; keep them in step). A session started in a deload week gets `deload = true`, and the backend returns its planned values lowered by the factors in `Deload` and without "previous session" values, so the session screens need no deload logic. Deload sessions are left out of "previous session" values, `lastUsedWeight` and the client's progression trend and records (`trendPoints` in `utils/stats.ts`), but still count for volume and consistency.
- Daily stretching is a separate domain (`StretchService`, `/api/stretch`): one `StretchRoutine` per user with ordered `StretchItem`s (hold seconds or reps, optionally per side) and `StretchCheckIn` days (the client's local date). It has no library entries or muscles, so stretches never count toward volume or other stats; keep it that way. An optional daily reminder (`StretchReminderService`) is published through ntfy (`NtfyClient`, configured by `NTFY_BASE_URL`, `NTFY_TOKEN` and `APP_PUBLIC_URL`; off without a base URL): `StretchReminderJob` checks every minute and sends to the user's random topic at their local time unless they already stretched that day. The notification's "Done" button posts to the public `/api/stretch/reminder/done/{token}`, where the secret token stands in for a login. The job runs outside a request, so it can't lazy-load entities.
- Authorization is per user and lives in the services. Each service method resolves the user with `CurrentUserService.get(authentication)` (by the id on the `AuthenticatedUser` principal, never by username) and checks ownership through the split (e.g. `findByIdAndUserId`, or `workout.getSplit().getUser()`). New endpoints must do the same.
- Errors: throw the exceptions in `exception/` (`ResourceNotFoundException`, `UnauthorizedException`, `ConflictException`, `BadRequestException`). `GlobalExceptionHandler` maps them to HTTP responses.
- API docs: springdoc generates the spec at `/api/docs/openapi.json` and Swagger UI at `/api/docs` (`OpenApiConfig`, `springdoc.*` properties). Give a new controller a `@Tag`; a public endpoint also needs an empty `@SecurityRequirements` (and a `permitAll` in `SecurityConfig`).
- Auth: short-lived JWT access tokens (`JwtAuthenticationFilter`) plus single-use, rotating refresh tokens stored in the DB (`RefreshTokenService`). `/api/auth/**` is public and everything else under `/api/**` requires a token. The token subject is the user id, never the username: usernames can change (`/api/account`) or be freed by account deletion, and the filter loads the principal by id on every request.
- Rate limits (in memory, `auth.rate-limit.*` in application.properties): `AuthRateLimitFilter` (in the security chain after CORS, before auth) limits login, register, refresh and the stretch "Done" link per client IP, and `AuthService.login` limits attempts per username (case-insensitive, reset by a successful login); over the limit is a 429 with `Retry-After`. The client IP comes from `ClientIpResolver`, which believes X-Forwarded-For only from `auth.rate-limit.trusted-proxies` (set for Nginx in `docker-compose.yml`). Tests set high limits in `src/test/resources/config/application.properties`.
- Schema is owned by Flyway (`src/main/resources/db/migration/V<n>__*.sql`) with `ddl-auto=validate`. Schema changes need a new migration and matching entity changes; never edit an applied migration.

### Frontend
- Expo Router file-based routes in `app/`: `(auth)` for login/register, `(tabs)` for the main tabs, and other screens and modals registered in `app/_layout.tsx`.
- The main tabs are a swipeable pager (material top tabs: a native ViewPager on Android/iOS, JS responders on web) with the custom `FloatingTabBar`. A horizontal pan inside a tab must be a gesture-handler `Gesture.Pan` (as in the charts' `scrubGesture`), since the pager takes the touch before a `PanResponder` responds, and must use `useTabSwipeLock` so the web pager stays still. `providers/AuthProvider.tsx` redirects between the auth and tab groups based on auth state.
- All HTTP calls go through the domain objects in `services/api.ts` (`authApi`, `accountApi`, `splitsApi`, `workoutsApi`, `exercisesApi`, `libraryApi`, `trainingLogsApi`, `statsApi`, `stretchApi`). The API base URL is `EXPO_PUBLIC_API_URL` (default `localhost:8080`) on web, but native builds always use the hard-coded production URL. The axios interceptor attaches the access token and, on a 401, refreshes once (concurrent 401s share a single refresh) and retries.
- Tokens are stored via `services/storage.ts` (SecureStore on native, localStorage on web).
- Server state uses TanStack Query through per-feature hooks in `hooks/`. Query keys are in `constants/queryKeys.ts`. Zustand stores in `store/` hold only client state (auth, theme, dialogs).
- **Offline support** (`services/queryClient.ts`): the query cache is persisted to AsyncStorage for 7 days, and NetInfo drives `onlineManager`. Mutations that must survive offline and app restarts (the session's `updateExerciseLog`, `addExerciseLog` and `completeTraining`, and the stretch check-in and its undo) need a `mutationKey` plus a `setMutationDefaults` entry registering their `mutationFn` (and any invalidation, since hook callbacks are lost on restart). They are replayed via `resumePausedMutations` after the cache is restored, and the hook updates the UI optimistically. A session's mutations share `trainingScope(id)` so they replay in order. On startup without a network, `AuthProvider` keeps the user signed in using the cached user. The query cache is cleared whenever the session ends.
- Styling: NativeWind (Tailwind) classes backed by CSS variables. `constants/theme.ts` defines themes and palettes (dark/light and a custom accent), `getThemeVars` injects them at the root, and `tailwind.config.js` maps color names to `var(--color-*)`. Use theme color classes (`bg-surface`, `text-accent`, etc.) rather than hard-coded colors.
- `components/BodyMap.tsx` draws the front and back figure (geometry in `constants/bodyMap.ts`, one shape list per view, mirrored) used for exercise muscles, the muscle picker and the weekly volume heatmap. `components/ExerciseIllustration.tsx` draws the catalog drawings in the theme's colors, and `ExerciseThumb` falls back to a small body map.
- Row actions (edit, delete, ...) go in an `ActionMenu` ("⋮" button inside an `ActionCard`, which swaps the row's contents for the actions in place), not behind a swipe.
- Dialogs: use `alert`/`confirm` from `utils/confirm.ts` (themed, and they work on web) rather than React Native's `Alert.alert`.
